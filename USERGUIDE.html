1. What it is

OverlayConsole is a blank desktop GUI (graphical user interface) made of several independent windows. Each window can show the output of any shell command: you point the command at a named pipe (a special file that passes data from one program to another) and the text appears in the matching window. The windows remember their size and position, so you can arrange them side by side once and keep that layout.

One built-in function is included: a read-only memory survey. It maps your computer's RAM (random-access memory), shows what the operating system exposes about kernel, process and hardware addresses, what you can see as a normal user, and what needs root. It was written partly as a way to learn how memory addressing works on a modern Linux system.

2. Starting it

Requirements: Linux with a graphical session, Python 3 and its Tk library (python3-tk on Debian/Ubuntu). Nothing else needs installing.

cd /home/stoic/Documents/ClaudeProject/OverlayConsole
python3 overlayconsole.py

Only one copy can run at a time; starting a second prints "OverlayConsole is already running." The first launch creates the pipes/ folder with five named pipes in it.

To run just the memory survey as plain text in a terminal, without the GUI:

python3 -m memsurvey.survey

3. The windows

Control window

The small main window lists the five pipes and a Memory survey button. Click a name to show or hide that pipe's window. A filled circle (●) means the window is open, an empty one (○) means it is hidden. When a hidden or background window has unread text, its name turns green and shows (N new). A divider bar between the list and the usage notes can be dragged.

Closing the control window quits the program and closes the other windows. Closing a pipe window or the Memory window only hides it.

One taskbar entry and the system tray

The control window is the only OverlayConsole entry on the taskbar. Every other window (the grid, floating pipe windows, Memory survey) is a child of it: hidden from the taskbar and pager, and minimized and restored together with it.

If the optional tray library is installed (sudo apt install python3-pystray), a small terminal-style icon appears in the system tray. Minimizing the control window, or pressing Hide to tray, hides all windows; click the tray icon (or choose Show / hide in its menu) to bring them back exactly as they were. The tray menu's Quit closes the program. Without the library nothing changes except the single taskbar entry; minimizing then works normally.

The docked grid (first four pipes)

The first four pipes (alpha, bravo on top; charlie, delta below) are snapped together in one window as a 2×2 grid. Drag the horizontal divider to change the row heights. Drag the vertical divider in either row to change the column widths; the divider in the other row moves with it, so the grid stays aligned like a table. Resize the window and the proportions are kept. The divider positions are saved (as proportions) in state.json.

Because the four are one window, clicking any of their names in the control window shows or hides the whole grid. New text in the grid is marked as seen when the grid window loses keyboard focus (all four panes together); each pane still has its own mark seen and clear buttons. Any pipes beyond the first four (by default epsilon) stay as separate floating windows.

Pipe windows

One view per pipe, named for the pipe (alpha, bravo, charlie, delta, epsilon), either a pane in the grid or a floating window. Each has:

  • a status line (pipes/alpha   3 new or all seen),
  • mark seen – turn all bright text grey (see section 5),
  • clear – empty the window,
  • vertical and horizontal scrollbars (long lines are not wrapped). The window follows new output only when you are scrolled to the bottom, so you can scroll up and read without being yanked down.

Each window keeps its most recent 20,000 lines; older lines are dropped.

4. Sending data into a window

The pipes are ordinary Linux named pipes (made with mkfifo). Anything that can write to a file can feed a window — no special tool is required.

echo "hello" > pipes/alpha
ping -c 5 localhost > pipes/bravo
dmesg | tee pipes/charlie            # tee also shows it in your terminal
tail -f /var/log/syslog >> pipes/delta
journalctl -f > pipes/epsilon
cat notes.txt > pipes/alpha

Use the full path (or run from the project folder as above). Each line you write becomes one line in the window; text is decoded as UTF-8 and unprintable bytes are replaced.

The console must be running. A named pipe with nobody reading it makes the writer wait (block) until a reader appears. If you run echo hi > pipes/alpha while OverlayConsole is closed, your terminal will appear to hang until you start OverlayConsole (or press Ctrl-C). Saving the output to log files when the console is closed is planned but not built yet.

Reaching the pipes from anywhere

A shell treats > alpha as a file called alpha in the current directory, so the bare name cannot be looked up automatically. Several plain-shell shortcuts get close, and the script setup-access.sh in the project folder offers them as a menu:

./setup-access.sh            # choose by number, e.g.  1 2 3   (asks before changing anything)
source ./setup-access.sh     # same, and reloads ~/.bashrc in your current shell afterwards
#OptionThen you can write
1Symlink ~/oc to the pipes foldermake 2>&1 | tee ~/oc/alpha
2Variable $OC in ~/.bashrcmake > $OC/alpha 2>&1
3One shell function per pipe name in ~/.bashrc (names that are already commands, such as echo, are skipped)make 2>&1 | alpha
4Symlinks to the pipes in a directory you choosemake > alpha 2>&1 (in that directory)
5Remote over SSH (instructions only)cmd | ssh you@host 'cat > ~/oc/alpha'
6Remote via a socat listener plus SSH tunnel (instructions only)see the script's output

Options 2 and 3 write a marked block into ~/.bashrc; running the script again replaces that block rather than duplicating it. A script cannot change the shell that launched it, so run it with source to have ~/.bashrc reloaded for you, or accept the offer to open a fresh shell. Note that cmd > pipe 2>&1 sends errors too, while cmd 2>&1 > pipe does not (the order matters). Remote options need your own SSH access; the script never reads ~/.ssh, and a socat listener has no authentication, so keep it bound to 127.0.0.1.

Showing output from a remote machine

Nothing needs to be installed on the remote machine beyond its SSH (Secure Shell) server, which it almost certainly runs already. The simplest method is to pull: run the command on the remote machine over SSH from here, and redirect what comes back into a local pipe.

ssh user@remote 'journalctl -f 2>&1'    > ~/oc/alpha
ssh user@remote 'make -C /srv/app 2>&1'   > ~/oc/charlie
ssh user@remote 'dmesg -w' | tee ~/oc/delta

The remote command's output travels back over the SSH connection and the local redirect writes it into the pipe. Put 2>&1 inside the quotes so it applies on the remote machine. If SSH logins to that host already work from here, this works too; the remote machine needs no access back to this one.

  • If output arrives late or in bursts, run the remote command under stdbuf -oL (part of coreutils, normally already present): ssh user@remote 'stdbuf -oL cmd'.
  • For long-running streams add -o ServerAliveInterval=30 so a dropped connection is noticed.
  • If the connection drops, the window stays open; just run the command again.

The opposite direction, pushing from the remote machine (setup-access options 5 and 6), needs that machine to be able to reach this one over SSH or through a socat listener here. Even then the remote side needs only bash: some_cmd > /dev/tcp/127.0.0.1/9001 through an SSH reverse tunnel (ssh -R). Prefer the pull method unless the remote machine must start the connection.

5. Seen vs. new text

New text is drawn in bright green. Text you have already seen is dim grey. A yellow ─── new ─── line marks where the unread block begins.

Text becomes "seen" when you press mark seen in that window, or when keyboard focus leaves OverlayConsole entirely (you click on another application). Moving between OverlayConsole's own windows does not mark text as seen. After that, the next line to arrive starts a fresh new block below the grey text.

Seen/new status lasts only while the program is running; it is not yet saved between sessions.

6. What is remembered

The file state.json stores, for every window: its size and screen position, whether it is shown or hidden, the divider positions of the control window and of the docked grid (as proportions, so they scale if you resize), and which Memory-survey tab was last open. It is saved shortly after any change and on exit. If a saved window would fall off a smaller screen, it is moved back on. On X11 desktops (e.g. LXQt, Xfce) each window's virtual desktop (workspace) is also remembered and restored on start, using xprop, xwininfo and wmctrl (optional; without them, or on Wayland, the windows simply open on the current desktop). Deleting state.json resets all layout to defaults.

7. Memory survey

Click Memory survey in the control window. Everything on these tabs is read-only: the program reads information the kernel publishes under /proc and /sys and never writes to memory or devices (the single exception, the MMIO trace, is described in section 9).

Toolbar. refresh re-reads the current tab. Elevate (root)… is explained in section 8; next to it is the current mode (user or ROOT helper). send tab to pipe copies the whole current tab into the pipe window you choose, so a survey can sit beside other output. Tabs load the first time you open them and are not updated automatically; press refresh to update.

Summary

Memory totals from /proc/meminfo (total, free, available, cache, kernel data, huge pages...), the page size (the smallest unit the kernel hands out, 4096 bytes) and the memory-hotplug block size. Below it is a table of what this user can see: for each address-bearing source, whether it is ok, masked (readable, but addresses replaced with zeros) or denied. This table is the quickest way to see what root unlocks.

Physical

The map of physical addresses — where things really sit on the memory bus.

  • Firmware memory map (e820 table from the BIOS/UEFI): ranges of RAM, reserved areas and ACPI tables with real addresses, readable without root. Notice the gap just below 4 GiB: RAM jumps over a region used by device registers, then continues above 4 GiB.
  • Kernel resource tree (/proc/iomem): the nested list of who owns each range (RAM, PCI devices, drivers). Addresses show as zero unless root, but the names and nesting remain.
  • Memory blocks and the zone free lists (/proc/buddyinfo): how much free memory exists in each region (DMA below 16 MiB, DMA32 below 4 GiB, Normal above) and in blocks of what size.

Kernel

Counts of kernel symbols by type (code, data, etc.), the largest loaded modules, and a reference table of the x86-64 kernel virtual address layout (user space, the direct map of all RAM, the vmalloc area, the struct page array, kernel code and modules). Symbol and module addresses are zeroed without root. The layout table is a fixed reference; the real bases are shifted at boot by KASLR (kernel address space layout randomisation).

Processes

Walks every process you are allowed to inspect and groups its virtual address space by category: heap, stack, shared libraries, program files, anonymous memory, shared memory, special kernel pages (vdso/vvar), and named allocator regions. It also totals by permission (read/write/execute) and ranks the top 20 processes by PSS (proportional set size: RAM actually used, with shared pages divided among sharers). Large "virtual" numbers against small RAM numbers are normal — most reserved address space is never touched.

Inspect PID: type a process ID and press Enter (or show map) to list that process's address ranges with permissions, size, category and mapped file. back to overview returns to the summary. Other users' processes are denied unless elevated.

Hardware

PCI devices with their vendor:device ID, class, bound driver and the address ranges (BARs, base address registers) where their registers live; legacy I/O port ranges; and the busiest interrupt lines. Device registers are shown as physical addresses, which you can match to the "reserved" holes on the Physical tab.

8. Elevating to root

The GUI always runs as your normal user. When you click Elevate (root)… the system's standard authentication dialog (polkit, via pkexec) asks for your password. On success a small helper program starts as root and the label turns orange: ROOT helper (uid 0). Your password is handled by the system dialog; OverlayConsole never sees or stores it. If you cancel, you simply stay in user mode and the status line says so.

While elevated, every tab is re-read as root, so zeroed addresses in /proc/iomem, /proc/ioports, kernel symbols, module load addresses and PCI maps show real values, and the Processes tab can see all users' processes. Click Drop root to end the helper and return to user mode.

The Privileged tab

Available only while elevated. Numbers can be decimal or hexadecimal (0x...).

ToolWhat it does

virtual → physical (pagemap)Fields: PID, virtual addr, pages. Shows, for each 4 KiB page, the physical frame number (PFN) it lives in, the resulting physical address, and flags (present, swapped, file/shared, exclusive, soft-dirty). This is the actual virtual-to-physical translation the CPU performs.
hexdump /dev/memFields: physical addr (shares the box with virtual addr), bytes. Reads raw physical memory. This kernel restricts /dev/mem (STRICT_DEVMEM) to non-RAM ranges and the first 1 MiB, so most RAM addresses are refused by design.

Errors (unmapped address, permission refused, bad number) are printed in the tab rather than crashing anything.

9. I/O capture

The I/O tab shows what hardware is doing. It has two independent modes and a mirror to pipe checkbox that also copies the output into the pipe chosen in the toolbar.

Counter sampling (no root needed)

Press ▶ sample counters. Once a second the tab shows what changed: interrupts per second per device (timer, disk controller, graphics, network card...), disk read/write bytes per second, and network receive/transmit rates, with running totals since you pressed start. Press the button again (■ stop sampling) to stop.

MMIO trace (root)

MMIO (memory-mapped I/O) means a device's control registers appear as addresses in the memory map; reading and writing those addresses is how drivers talk to hardware. The ▶ MMIO trace button turns on the kernel's mmiotrace facility and lists each register read or write, decoded like this:

   3.500000 READ  4B phys=0xe0000008 value=0x00001234 [0000:00:02.0 i915 BAR2+0x8] map#1

Fields: timestamp, read or write, width in bytes, physical address, value, then which PCI device, driver and BAR (and offset into it) that address belongs to.

  1. Click Elevate first. You will be asked to confirm starting the trace.
  2. The trace only sees devices whose driver maps its registers after the trace begins. To observe a device, reload its driver, for example the network card: 
    sudo modprobe -r e1000e && sudo modprobe e1000e
    This briefly drops that device (and your network). Use a device you can afford to interrupt.
  3. Press ■ stop MMIO trace, Drop root, or quit to end it. All three restore the kernel tracer to its normal "off" state. If another tracer is already active, OverlayConsole refuses to start rather than replace it.

Only memory-mapped registers are captured. Old-style x86 port I/O (in/out instructions) is not traced. Tracing slows the machine while running.

10. Configuration and files

Renaming or changing the pipes

Create config.json in the project folder:

{ "pipes": ["logs", "net", "build", "debug", "misc", "extra"] }

Names must be unique and look like variable names (letters, digits, underscore; not starting with a digit). Any number of pipes is allowed, not only five. If the file is missing or invalid, the default five are used. Restart to apply. Old pipe files and saved layout for removed names are simply ignored.

11. Troubleshooting

My command hangs when I write to a pipe.
OverlayConsole is not running, so nothing is reading. Start it, or press Ctrl-C.
"OverlayConsole is already running."
A copy is already open (check for hidden windows or run pgrep -af overlayconsole). A stale lock after a crash clears itself, because it is released when the process exits.
A window is missing.
It is hidden: click its name in the control window. If the position is off-screen, delete state.json and restart.
Elevate does nothing or says pkexec not found.
Install polkit (sudo apt install policykit-1) and make sure a polkit authentication agent is running in your desktop session.
"authentication cancelled or denied".
You closed the password dialog or typed it wrong. Press Elevate again.
hexdump says "Input/output error" or "Permission denied".
The address is not mapped in that process, or the kernel refuses (ptrace rules, or /dev/mem limits on RAM). This is the kernel protecting memory, not a bug.
MMIO trace shows nothing.
Expected until a driver maps its registers after the trace starts; reload a driver (section 9).
Tabs look out of date.
Tabs load once. Press refresh.

12. Safety notes

The survey and all root tools only read. The helper accepts a fixed list of commands, limits each read to 4096 bytes, and validates every argument. Its only writes are the fixed on/off settings of the kernel tracer used by the MMIO trace, which are always switched back.
  • Reading another process's memory or raw physical memory can expose passwords, keys and private data on screen, and via mirror to pipe or send tab to pipe into anything attached to a pipe (such as a file with tee). Only use it on a machine you own.
  • The root helper file memsurvey/helper.py lives in your project folder and is run as root. Any program running as you could modify that file before you next click Elevate. This is acceptable for a personal learning tool; do not deploy it to a shared machine without installing the helper in a root-owned location.
  • Pipes are owner-only (mode 0600), so other users cannot write to them.
  • Reloading drivers for the MMIO trace interrupts the device. Do not do this for your only disk controller or network link.

13. Glossary

Named pipe (FIFO)
A file-like object that one program writes into and another reads from, in order. First in, first out.
Physical address
A location on the actual memory bus, as the hardware sees it.
Virtual address
The address a program sees. The CPU translates it to a physical address through page tables, a block of 4096 bytes at a time.
Page / PFN
A page is one 4096-byte unit of memory. The PFN (page frame number) is a page's physical position: physical address = PFN × 4096.
Kernel
The core of the operating system, which manages memory and hardware.
/proc and /sys
Virtual folders where the kernel publishes live information as readable files.
KASLR
Kernel address space layout randomisation: the kernel loads at a random offset each boot to make attacks harder.
kptr_restrict
A kernel setting that hides kernel addresses from non-root users (shown as zeros).
ptrace / Yama
The kernel's debugging interface and the security rule (ptrace_scope) that limits which processes may read each other's memory.
PCI / BAR
PCI is the bus most hardware devices sit on. A BAR (base address register) tells the system where in the address map a device's registers are placed.
MMIO
Memory-mapped input/output: device registers accessed as if they were memory addresses.
Interrupt (IRQ)
A signal from hardware asking the CPU for attention, such as "a packet arrived".
Driver / module
Kernel code that operates a particular piece of hardware; a module is a driver that can be loaded and unloaded.
polkit / pkexec
The standard Linux system for asking for administrator permission through a dialog instead of running a whole program as root.
tracefs / mmiotrace
The kernel's tracing interface, and the tracer within it that records memory-mapped register accesses.
